# CI reference

What each local pre-push tier and each CI lane does, and the history behind the concurrency and burst rules. The private rules (`.savoir/platform/AGENTS.md`) keep only the push procedure. Read this file when a gate fails and you need to know what it checks, or when you are diagnosing a missing or cancelled run.

## Local pre-push tiers and CI lanes

The surfaces, each commented with why in the script and printed by `--list-surfaces`: `migrations/`, `migrations_pg/` and the two `crates/pierre-database` links its `sqlx::migrate!` calls embed through; `infra/modules/secrets/` and `infra/modules/kms/`; the athlete-facing send modules (the Resend send path, the notification dispatch facade, triggers and push-tier policy with its persona gate, the channel sink, the proactive channel send, the outbound retry worker, the digest and follow-up schedulers, the group chat poster — renderers and user-requested emails are left out on purpose); and an added non-comment line outside Markdown that replaces a Cloud Run service's whole secret set (`gcloud --set-secrets`/`--clear-secrets`, deploy-cloudrun's `secrets_update_strategy: overwrite`). It fails closed when a listed path no longer exists in HEAD or a `sqlx::migrate!` call embeds a directory no surface covers, so the list cannot go stale silently, and when the base shares no history with HEAD. A commit message belongs to the push that carried it, so the gate judges that range or nothing: it takes its base without `gate-base-ref.sh`'s HEAD~1 fallback, and a base naming no range — HEAD itself, a commit ahead of HEAD, or one the checkout lacks — judges nothing rather than the tip's message alone, which would fail a burst push whose ONE-WAY line sits on an earlier commit. Pre-push hands it `$GATE_BASE_REF` or `origin/main` as given, and the fast gate judges the same commits: a pull request's base, a push to main's before-sha, and a branch push's fork point from main — never a branch push's own before-sha, which covers that push alone and would fail a second push re-touching a surface the branch's first push declared, after pre-push passed it; the self-test lifts that step out of `ci-backend.yml` and runs it. Runs its self-test `check-merge-risk.test.sh` when the gate, the self-test or `ci-backend.yml` changes; CI's fast-gate runs the gate on the push and pull_request events ci-backend fires on (never schedule or dispatch, which carry no push range), whose paths include the two infra modules for this gate, and the self-test on every run), Tier 1p `scripts/ci/check-unused-deps.sh` (compile-free, ~2s; the coding standards forbid a phantom dependency, and the first scan found 87 issues across 24 crates. It runs `cargo shear --deny-warnings --locked` over every workspace member — cargo-shear parses each target's source, lib, bins, tests, benches and examples, without compiling and regardless of `cfg` — and fails on a dependency no target names, an optional dependency nothing names, a normal dependency only tests use (move it to `[dev-dependencies]`), a `[workspace.dependencies]` entry no member inherits, or a source file no module tree reaches. A dependency that is needed but never named in source, such as a feature-unification edge, is ignored in its own crate with `[package.metadata.cargo-shear] ignored = ["name"]` and a one-line reason above it, never in `[workspace.metadata]`; cargo-shear reports an ignore that suppresses nothing, so a stale one fails too. The gate also fails when cargo-shear is missing or not the pinned version (`check-unused-deps.sh --pinned-version`, installed with `cargo install --locked cargo-shear@<that version>`), when it crashes, when its JSON report is missing or disagrees with its exit status, and when the workspace has no member to scan. Runs when a manifest, `Cargo.lock` or any `crates/**/*.rs` changes, since deleting the last `use` of a crate leaves its manifest line unused, and its self-test `check-unused-deps.test.sh` when the gate or the self-test changes. CI's fast gate installs the pinned version with `taiki-e/install-action` and runs the self-test and the gate on every push; the self-test fails when the workflow's pin and the script's differ), Tier 5 frontend, Tier 6 SDK, Tier 7 mobile.
- **A new chat surface, reply block, or notification screen is generated, not written.** `GET /api/surfaces/capabilities` serves the `SurfaceProfile::resolve` table; `cd packages/shared-constants && bun run generate` rewrites `src/surface-capabilities.generated.ts` from a running server, exactly as `packages/mcp-types` regenerates from the tool registry. Both clients read that file — the registry's per-surface `blocks` column, the notification screen vocabulary — so Tier 1d fails the push while it is behind the Rust source.
- **Scoped lanes (carnet#1282, JF's directive of 2026-10-30; supersedes the 2026-08-31 branch-lane contract of carnet#154):** `ci-postgres.yml` and `ci-backend.yml`'s `leaf-crate-tests` test what a push can change, judged against a proven base. `scripts/ci/scope-base.sh` names the base: on any branch, its fork point from main (never the branch's previous push); on main, the newest ancestor whose run of that lane passed every one of its jobs — success, not skipped — so main tests what changed since the last tree it proved, anchored at a full run (the daily schedule, a dispatch, or any push judged full). `scripts/ci/affected-crates.py scope` judges the diff from the base: a crate's files reach it and every crate depending on it, through dependencies of any kind (the graph read from `Cargo.lock`, which needs no toolchain; the leaf job's `check-graph` step holds it to `cargo metadata`); `Cargo.lock` reaches the crates resolving an entry that differs; the root `Cargo.toml` reaches the crates naming a changed `[workspace.dependencies]` entry, and everything when anything else in it changes; a file outside `crates/` reaches the crates `check-rust-inputs.py`'s scan finds reading it (or symlinking it, like pierre-database's migrations); a crate's own `tests/`, `benches/` or `examples/` sources reach its tests alone. The toolchain, `.cargo/`, `clippy.toml`, the definitions the scoped lanes run (their workflows, actions and scripts), the trees the server builds from whole (`migrations*/`, `templates/`, `commands/`, `sdk/`, `test_data/`) when no crate is found reading the path, and anything unclassified test every crate; a lookup or classification that fails does too. `leaf-crate-tests` runs the crates in scope (none is a green answer, with a notice); the PostgreSQL lane runs the full suite (every suite `scripts/ci/server-suites.sh list` names, ~21-24 min) when the diff reaches `pierre_mcp_server`'s build — 89 of the last 100 main commits did — and otherwise the `*_postgresql_test.rs` smoke plus the targets of the server test files the push edits. Each run's `Choose the crates this push can change` / `Choose the lane` step logs the base and why. **A scoped run is never a proof:** main's exact-tree skip (below) requires the step that runs only on a full selection — `Leaf-Crate Tests (every crate but pierre-server) -> Every leaf crate is in scope`, `Build Test Binaries (PostgreSQL) -> The lane is the full suite` — not merely the job. `server-suites.sh changed-targets` (pre-push, `dev-tests`) classifies through the same `affected-crates.py classify-server`, with no base, so `Cargo.lock` and the root manifest answer every target there. For a full verdict on any ref, dispatch ci-postgres. Coverage (~92 min, batched) is a SQLite run that fires weekly (Sunday 03:17 UTC), on `workflow_dispatch`, and on PRs — never on push, so it holds no slot during a main burst — and it is not a PG gate.
- **Rust-input gate and the release binary (carnet#1114):** `ci-backend.yml`'s compile and test jobs run only when a push touches a path in the `rust` filter of `.github/actions/ci-backend-changes/action.yml` — the crates, the manifests and toolchain, migrations, and the non-Rust files Rust code reads (locales, `activity-sports.json`, mcp-types, `tokenLink.ts`, `sdk/`, dev `.tf`, `commands/`, the frontend nginx headers, `scripts/ci/`). `fast-gate` always runs. `scripts/ci/check-rust-inputs.py` (fast-gate) fails when a crate reads a file outside `crates/` the filter misses, or when a filter glob is missing from the workflow's own `paths`. The fat-LTO `release-binary` runs on main when `rust` is set, and on a branch only for a link input (`release-worthy`: root `Cargo.toml`, `build.rs`, `.cargo/`, the toolchain, `docker/images/server/`, `rust-setup`, `server-binaries`, the workflow); every other branch push gets `server-e2e.yml`'s size check on the thin binary (ceiling 139 MB, the fat 115 MB scaled by measured sizes — move both together). A main push uploads `server-binaries-<sha>`, which `publish-images.yml` deploys instead of compiling release-lto again; with no artifact (a non-Rust push, or one older than three days) it compiles. The SQLite shards run on the daily cron, or on a dispatch that sets `sqlite-shards` (the bump gates' dispatches never do). **Build once (carnet#1115):** the PostgreSQL lane and the cron SQLite shards each have one job that compiles every test binary the lane runs (`scripts/ci/test-binaries.sh build`, which also reports the runner's peak memory) and four shards that download, `unpack` and run them (`server-suites.sh run --binaries`, which execs through `test-binaries.sh run`, as pierre-database's files do) without a toolchain; `server-e2e.yml` builds the thin-release server and `pierre-cli` once for the Playwright, MCP compliance, SDK and examples-smoke lanes. `scripts/ci/ci-time-report.py --since --until` re-measures job-hours, runner wait and the two time-to-green targets with the 2026-10-21 baseline's method; `scripts/ci/cache-budget.py` (the daily lane monitor) reports the Actions cache per family against its 10 GB quota.
- **Server test layout:** most `crates/pierre-server/tests` suites are modules of one binary, `tests/it/main.rs`; a suite that writes the process environment stays a top-level file and its own binary (`it/test_layout_test.rs` fails either drift). `scripts/ci/server-suites.sh` reads the `it` suites from the `mod` lines of `it/main.rs`, shared `helpers` included, and is the one place that maps a suite name to how it runs — `list`, `targets`, `run` — and every lane that shards, lints or runs server suites by name goes through it. A suite of `it` runs as a `<module>::` libtest filter, a substring match, so `server-suites.sh it-args` adds a `--skip` for every other module whose name ends the same way (`routes_test::` alone selected 198 tests, 4 of them its own); a skip that would also hit a wanted module is left out. The PostgreSQL shards are packed by `.github/ci-postgres-test-durations.tsv`; `scripts/ci/refresh-pg-shard-weights.sh <run-id>` rewrites it from a green full-suite run, weighing an `it` module by its share of the `it` run's wall clock.
- **Server test scoping (`server-suites.sh changed-targets`):** maps changed paths (stdin) to the `--test` targets whose outcome they can change, through `affected-crates.py classify-server` (the classifier the scoped lanes read). A path that reaches `pierre_mcp_server`'s build — a file of any workspace crate in its dependency closure (every dependency kind, dev included, read compile-free from `Cargo.lock`, so a new crate needs no edit), a file outside `crates/` a closure crate reads or symlinks (a locale, a migration, a `.tf` the tests hold the code to), a file of another member that a closure crate embeds, a non-`.rs` file under the server's `tests/` — answers with EVERY target (`it` plus each top-level suite), as do the workspace manifest and `Cargo.lock` (no base to diff them against here), the toolchain pin, `.cargo/`, the trees the server builds from whole (`migrations*/`, `templates/`, `commands/`, `sdk/`, `test_data/`) when no crate is found reading the path, and any path it cannot classify. A closure crate's top-level `*.md` and the `.rs` of its own `tests/`/`benches/`/`examples/` name none (the leaf-crate lane runs those); so do docs, the clients, scripts and CI config. An edited server test file names its own target; `common.rs` and `tests/helpers/` name `it` and every top-level suite declaring `mod common;`/`mod helpers;`. If the crate graph cannot be read, the answer is every target — planning is an optimisation, and a planner failure must restore the whole run (the rule Apache Iggy's cargo-rail planner follows). `--edited-only` keeps only the targets whose test source the diff edits, and is what `preflight-clippy`, pre-push Tier 1e, the pre-push clippy advisory and `ci-postgres.yml`'s smoke (the targets it adds to the `*_postgresql_test.rs` suites) use: linting every target on any src change would compile the server's whole test graph locally, and the full-workspace `clippy` job lints them all in CI anyway. `scripts/ci/server-suites.test.sh` pins the mapping, including the unreadable-graph path.
- CI fires parallel jobs on push (`ci-backend.yml`: `fast-gate` ~30s, `preflight-clippy` ~3–5min, `clippy` ~10–12min, `security-audit`, `dev-tests` ~10–12min, `release-binary` ~18min in parallel with clippy; plus `ci-postgres.yml`, `server-e2e.yml`, `frontend-tests.yml`, `mobile-unit-tests.yml`, each path-scoped). The two mobile E2E lanes (`mobile-e2e-ios.yml`, `mobile-e2e-android.yml`) do not run on push: they run nightly on main, or on a dispatch from main (carnet#1258). **A main push skips what a branch already proved:** `scripts/ci/proven-on-branch.sh` lists the jobs a `feature/`, `features/` or `claude/` push run passed on the exact tree being pushed to main, and the PostgreSQL lane, the Server E2E lanes and ci-backend's clippy, leaf-crate tests and feature profiles skip on main when theirs are listed (clippy when its lint step is: the job itself concludes green on a push no Rust input touches; `release-binary`, `fast-gate`, `dev-tests` and `security-audit` always run; a skipped job reads as green in `ci-verdict.sh`). **E2E server builds reuse identical inputs:** `.github/actions/prebuilt-server` downloads the binaries an earlier run uploaded under the `scripts/ci/server-build-key.sh` key of the same inputs, so a run whose Rust inputs were already built skips the compile. `cancel-in-progress` behaviour differs per workflow and it matters when diagnosing a missing run. **Protected on main:** every test-verdict push lane (`ci-backend.yml`, `ci-postgres.yml`, `frontend-tests.yml`, `mobile-unit-tests.yml`, `ci-redis.yml`, `server-e2e.yml`, … — `grep -l 'github.sha ||' .github/workflows/*.yml` is the live list) appends `github.sha` to the concurrency group when the ref is `main` (`...${{ github.ref == 'refs/heads/main' && github.sha || 'shared' }}`), so every commit gets its own group and nothing cancels or evicts another's verdict. `cancel-in-progress: false` alone is NOT protection: it keeps a running run alive, but a group holds one waiting run and the next push replaces it with zero jobs started — under a ref-only group `ci-postgres.yml` lost 9 of 84 main verdicts that way (carnet#169; runs 33450894413, 33552222435, 33555424548). **Still evictable on main, by design:** `chat-conversation-eval.yml` groups by ref alone with `cancel-in-progress: false`, so its push run can be replaced while it waits behind a live-llm run; `terraform.yml` (`terraform-state`) also groups without the sha, because a newer plan superseding a waiting one is the intended behaviour, not a lost verdict. So a missing `ci-backend`/`ci-postgres` run on main is NOT a cancellation and needs another explanation (usually the commit was not the tip of its push — see below), while a missing `chat-conversation-eval` run may well be. Read the workflow's `group:` expression before blaming cancellation.

## Burst pushes and per-commit validation

**A push's CI run belongs to the TIP, not to each commit.** GitHub fires one run per push, so a push carrying three commits produces one run, on the third. That run tests the tip's TREE — which contains all three — so a break that survives to the tip IS caught normally. Main's health is covered.

What a burst does NOT give you is per-commit validation, and that costs you in two places: `git bisect` can land on a tree nothing ever ran, and reverting one commit out of a burst produces a combination no run has seen. A commit broken and then fixed inside the same burst is invisible, which is harmless.

**Do NOT push commits one at a time to get per-commit runs.** `8897e9312` exists because burst pushes queued one deploy per push — 60 commits on 2026-08-26 became 44 image builds, each a full cargo-chef build pulling the multi-GB registry buildcache back as billed egress. Batching is the cheap direction and the fix now collapses bursts deliberately.

**The real exposure is the window, not the batching.** On 2026-08-28 a commit adding a 13th system prompt without updating the counts that pin it went up in a burst; the tip's run reported `failure` correctly — 31 minutes later. Nothing was red in between because the run was still in flight, and nobody was watching it. An unrelated feature branch hit the break first. So: after pushing to main, watch the run to terminal (below). That is what would have caught it, not a different push shape.

**When a run is genuinely ABSENT** — no row for that SHA at all — do not reach for "it was cancelled" without checking; on `ci-backend`/`frontend-tests` a main commit cannot be cancelled, so the explanation is that the SHA was never a push tip:

```bash
git log --oneline <base>..origin/main        # every sha that landed
gh run list --branch main --limit 15 --json headSha,conclusion,status
```

## One verdict per commit (`ci/verdict`)

**Is this sha green? Ask `scripts/ci/ci-verdict.sh <sha>`, or read the `ci/verdict` commit status — never enumerate lanes by hand.** Our lanes are ~20 separate, path-scoped workflows, so no `needs:` can join them into one required check the way a single-workflow repo's final job does (Apache Iggy's `finalize_pr`, which `needs:` every lane with `if: !cancelled()`). Enumerating them by hand is how a red `Deploy: Build & Ship (dev)` sat unnoticed for twelve hours: it is not a `CI:` lane.

- **What it computes.** (1) The push: `--before`, else the repository activity API's push whose `after` is the sha, else the commit's own parent; an all-zero `before` (a new branch) diffs from its merge-base with `origin/main`. (2) The expected workflows: every workflow file *at that sha* whose `on.push` matches the branch (`branches`/`branches-ignore`) and at least one changed file (`paths`/`paths-ignore`, GitHub's glob rules); a tags-only trigger never fires on a branch push, and `[skip ci]` expects nothing. (3) The actual runs, `GET actions/runs?head_sha=<sha>` over REST, push and `workflow_run` events on that branch, newest per workflow file. A `workflow_run` lane (the deploy and its post-deploy check) cannot be predicted from the push, so it is scored once it has run — GitHub stamps it with the branch tip at the moment it fired, so its title is printed to show which sha it acted on.
- **The verdict is the exit status:** `0` green — every expected lane concluded `success` (or `skipped`/`neutral`); `1` red — any `failure`/`cancelled`/`timed_out`/other conclusion, any expected workflow with **no run at all** (fail closed; a push of more than 300 files says so, since GitHub's path filter reads only 300), or nothing verified the sha; `3` pending — no red yet and a run still queued or in progress; `2` error — the runs could not be read, the sha is not in the checkout, or no branch could be inferred (pass `--branch`). A failed API call is an error, never "no runs". A cancelled run is red even where cancellation is by design (a branch lane superseded by a newer push, `chat-conversation-eval.yml`'s evictable group): the verdict is about this sha, and that sha was not verified.
- **`.github/workflows/ci-verdict.yml`** re-runs it on every `workflow_run` completion of the lanes it lists, on `main`, `feature/**`, `features/**` and `claude/**`, and publishes the result as the commit status `ci/verdict` (state `success`/`failure`/`pending`/`error`, the verdict line as description, the run as target URL), so the last lane to finish leaves the final word. It checks out the default branch and reads the judged sha's workflow files and diff only as git objects — nothing from that sha executes. It cannot recurse: it is not in its own trigger list and the script never scores its runs. `scripts/ci/ci-verdict.test.sh` (fast gate) pins green, red, cancelled, missing, pending, a path-filtered lane excluded, downstream and self runs, the API-failure paths, and fails when the trigger list misses a workflow a branch push can fire.

## Private repos out of Actions minutes

**Private dravr repos can run out of Actions minutes** (the org is on GitHub's free plan; it happened 2026-09-22). A private repo's run then sits `queued`, or fails with "The job was not started because recent account payments have failed…" and zero steps — a bill, not a broken build. The procedure is ChefFamille's (carnet#534): **public → CI → private**, and a red CI leaves the repo private until a new push. Never hand-roll it — `.claude/skills/private-ci/private-ci.sh check` says whether the limit is hit, `run <repo> <checkout> [--release …]` scans the whole history for secrets first, and flips back to private on any exit. It refuses dravr-carnet, dravr-vault and dravr-savoir. dravr-platform, dravr-embacle and dravr-tronc are public and unaffected.
